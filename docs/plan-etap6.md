## 1. Що просив замовник

Дослівно (2026-09-18):

> У налаштуваннях при двобічній синхронізації має бути пункт «Погодження змін». Якщо його
> активовано, то при будь-яких змінах у кінцевій теці (видалення, переміщення, зміна файлу,
> перейменування тощо) фіксується така подія, але фактично нічого не відбувається.
> У вікні «Останні зміни» зверху з'являється пункт «Виявлено зміни, які потребують погодження».
> Вікно зі списком: початковий файл (назва, розмір, шлях) → іконка типу модифікації → змінений файл
> → кнопки лише з іконками: підтвердити, скасувати, повернути. Зверху — «Підтвердити усі»,
> «Скасувати усі», «Повернути початковий стан». Видалено — червоним, додано — зеленим.
> Підтвердження = зміна застосовується у вихідній теці; скасування = у вихідній нічого не
> змінюється, у кінцевій лишається змінений варіант; «Повернути початковий стан» = кінцева тека
> повертається до початкового стану. Плюс чекбокс «Версіонування файлів»: створюється тека
> `.wfsversions`, куди потрапляють змінені файли, які ми відкочуємо назад; ця тека не синхронізується.

## 2. Що це змінює в моделі продукту

Досі кожен прохід був **автоматичним і завершеним**: спланував — виконав — записав стан. Погодження
вводить третій, принципово новий стан об'єкта: **«зміну помічено, рішення ще не ухвалено»**. З цього
випливає майже все інше в цьому плані:

1. **З'являється стан, що живе між проходами.** База стану (`entries`) описує «як було після
   останнього проходу». Черга погоджень описує «що відрізняється зараз і чому ми цього не чіпаємо».
   Це друга таблиця, а не колонка в першій: у однієї пари шлях може мати рівно один запис стану, але
   черга — це журнал подій із власним життєвим циклом (виявлено → вирішено).
2. **Планувальник уперше має право нічого не робити з відомим розходженням.** Сьогодні
   `TwoWayPlanner` на будь-яку різницю ухвалює рішення. Тепер частина шляхів **заморожена**, і
   заморозка має бути входом планувальника (чистим, як `PlanScope`), а не перевіркою всередині
   виконавця.
3. **«Скасувати» не може означати «нічого не робити».** Якщо після скасування просто лишити обидві
   теки різними, наступний прохід побачить ту саму різницю і спитає знову — і так довіку. Потрібен
   явний статус «розбіжність погоджена», і він має переживати зміну **лише другого** боку
   (див. §5.5). Без цього функція перетворюється на генератор нагадувань.
4. **«Повернути» вимагає, звідки повертати.** Для зміненого та видаленого файлу оригінал є у
   вихідній теці — додаткове сховище не потрібне. Але для файлу, **доданого** в кінцевій теці,
   «початковий стан» — це його відсутність, тобто відкат означає знищення даних користувача.
   Саме тому `.wfsversions` — не косметична опція, а умова безпечного відкату (див. §5.6).
5. **«Підтвердити» — єдина дія в продукті, що видаляє у вихідній теці за командою людини.** А
   вихідна тека замовника — Hetzner Storage Box через інтернет, де **Кошика не існує** і видалення
   остаточне (`docs/product/features/sync-modes.md`, «Видалення»). Тому підтвердження видалення має
   бути найзахищенішою дією у вікні, а не найлегшою.

## 3. Рішення, ухвалені при аналізі

1. **Тільки `twoWay`.** У дзеркалі джерело — read-only (інваріант playbook'а), тож «підтвердити»
   там не має куди застосуватися. Конфіг відхиляє `approval` на парі `mirror` так само, як зараз
   відхиляє `autoClean` на `twoWay`.
2. **Модерується один бік — «друга папка» (ціль).** У двобічному режимі боки рівноправні, тому
   в діалозі пункт підписується повним шляхом: «Погоджувати зміни в `D:\OneDrive\…`». Модерація
   обох боків одночасно — поза обсягом (це вже не синхронізація, а ручний менеджер злиття).
3. **Черга — в `state.db`, окрема таблиця, схема v3.** Міграція v2→v3 тривіальна (нова таблиця,
   старої не чіпаємо), механізм міграції вже є і перевірений. Пам'ятати: старіший білд відмовиться
   відкривати базу v3 — це навмисна поведінка `StateStore`.
4. **Перейменування й переміщення треба розпізнавати окремо.** Сьогодні рушій їх не знає: rename —
   це пара «зникло + з'явилося». Але макет рядка («початковий файл → іконка → змінений файл») має
   сенс саме для перейменування, та й підтвердження перейменування на віддаленому боці має бути
   `File.Move`, а не «скопіювати заново і видалити» (при RTT 48 мс різниця — години на великій теці).
   Потрібен окремий чистий компонент `MoveDetector` (§5.3).
5. **Кнопки треба перейменувати.** «Скасувати» в рядку означає «залишити як є, більше не питати», а
   «Скасувати» внизу діалогу — «закрити без змін». Два різні значення під одним словом у одному
   вікні — гарантована втрата даних через непорозуміння. Пропоновані підписи — §6.2.
6. **`.wfsversions` виключається з синхронізації жорстко, а не шаблоном.** Виключення (F6) редагує
   користувач; одне необережне очищення списку — і тека версій поїде в хмару або на сервер. Ім'я
   резервується у сканері поруч із перевіркою tombstone-тек.

## 5. Архітектурні рішення

### 5.1 Черга погоджень: таблиця `pending`

```sql
CREATE TABLE IF NOT EXISTS pending (
  id INTEGER PRIMARY KEY,
  pair TEXT NOT NULL,
  path TEXT NOT NULL,            -- шлях у МОДЕРОВАНІЙ (другій) теці
  from_path TEXT,                -- для rename/move: як було; інакше NULL
  change INTEGER NOT NULL,       -- added|modified|deleted|renamed|moved|conflict
  kind INTEGER NOT NULL,         -- file|directory
  src_size INTEGER, src_mtime INTEGER,      -- «початковий файл» (перша тека / останній відомий стан)
  dst_size INTEGER, dst_mtime INTEGER,      -- «змінений файл» (друга тека на момент виявлення)
  detected INTEGER NOT NULL,
  status INTEGER NOT NULL,       -- pending|approved|dismissed|reverted|stale
  resolved INTEGER,
  version_path TEXT              -- куди лягла копія при відкаті, якщо версіонування ввімкнене
) STRICT;
CREATE INDEX IF NOT EXISTS pending_open ON pending (pair, status, detected);
CREATE UNIQUE INDEX IF NOT EXISTS pending_one_per_path ON pending (pair, path) WHERE status = 0;
```

Чому окрема таблиця, а не колонки в `entries`:

- запис у черзі має **два боки одночасно** (було/стало) — `entries` описує один узгоджений стан;
- вирішені записи корисно потримати для журналу й розбору (`status != pending`), а `entries` має
  рівно один рядок на шлях назавжди;
- частковий унікальний індекс дає безкоштовну гарантію «одна відкрита подія на шлях»: повторне
  виявлення тієї самої зміни **оновлює** запис (нові розмір/час), а не плодить дублі.

`entries` при цьому **не змінюється взагалі**, поки рішення не ухвалено. Це і є «фактично нічого
не відбувається».

### 5.2 Заморожені шляхи: вхід планувальника, а не перевірка у виконавця

`TwoWayPlanner` отримує третій необов'язковий аргумент — `FrozenPaths` (множина шляхів + множина
тек-префіксів). Правила:

- шлях у множині → жодної дії, `Stats.AwaitingApproval++`, рядок `entries` не чіпається;
- заморожена **тека** заморожує все піддерево (видалення теки в другій папці не має тихо
  перетворитися на видалення її вмісту з першої);
- решта пари синхронізується як звичайно — заморозка точкова.

Це збереже інваріант «планувальник без файлового вводу-виводу» і зробить поведінку одиничним
тестом на таблиці рішень, а не інтеграційним.

**Зміна з першого боку поверх замороженого шляху** (у першій теці змінили той самий файл, який
чекає погодження) не виконується мовчки — інакше правка користувача в другій теці буде затерта ще
до того, як він її погодить. Запис у черзі переходить у `change = conflict`, у вікні він показується
окремим кольором і має додаткову дію «залишити версію з першої теки».

### 5.3 Розпізнавання перейменувань і переміщень (`MoveDetector`)

Чистий компонент без файлового вводу-виводу: на вхід — списки «зникло» і «з'явилося» в межах
**одного проходу однієї пари**, на вихід — пари «було → стало».

Правила склейки (усі мають виконатися):

- однаковий розмір **і** `mtime` у межах тієї самої 2-секундної допустимості, що й у планувальника;
- однакове розширення;
- **рівно один** кандидат з кожного боку; якщо на «зникло» претендують два «з'явилося» (типово:
  копія файлу) — склейки немає, показуємо як окреме видалення й додавання;
- порожні файли (0 байт) не склеюються ніколи — надто багато хибних збігів.

Тип події: та сама тека, інша назва → `renamed`; та сама назва, інша тека → `moved`; і те, й те →
`moved` з показом обох назв. Для тек — те саме за назвою й набором дітей.

Підтвердження `renamed`/`moved` у першій теці виконується як `Directory.Move`/`File.Move` у межах
кореня (одна операція), а не копіюванням.

### 5.4 Три рішення: що саме відбувається

Позначення: **A** — перша тека (вихідна), **B** — друга тека (модерована, «кінцева»).

| Подія в B | Підтвердити | Залишити як є | Повернути |
|-----------|-------------|---------------|-----------|
| Файл змінено | скопіювати B→A; рядок `entries` описує обидва боки | `entries` запам'ятовує обидва боки, статус `Diverged` | (версія B → `.wfsversions`), скопіювати A→B |
| Файл видалено | видалити в A (у Кошик, якщо він там є; інакше — попередження й обов'язкова копія у `.wfsversions`) | статус `Tombstone`: у A лишається, у B не з'явиться | скопіювати A→B |
| Файл додано | скопіювати B→A | статус `LocalOnly`: живе лише в B, більше не питаємо | перенести B-файл у `.wfsversions` і прибрати з B; без версіонування — у Кошик |
| Перейменовано / переміщено (файл або тека) | `Move` у A | `Diverged` на обох шляхах | `Move` назад у B |
| Теку додано | створити в A (разом із вмістом — один запис на теку, не на кожен файл) | `LocalOnly` на теку й піддерево | перенести теку у `.wfsversions` і прибрати з B |
| Теку видалено | видалити піддерево в A (через стелю §5.8) | `Tombstone` на теку (сканер її не обходить — механізм уже є) | відновити піддерево з A |
| Конфлікт (змінилось і в A, і в B) | лишити версію B, скопіювати B→A | `Diverged` | лишити версію A, скопіювати A→B |

Дії виконуються **тим самим `SyncExecutor`** через маленький одноразовий `SyncPlan`: жодного
другого коду, що вміє копіювати й видаляти. Це важливо — усі три запобіжники видалення (§4.5
етапу 5) продовжують діяти й тут.

### 5.4a Межа слова «тощо»: що програма вважає зміною, а що ні

У запиті сказано «будь-яких змінах (видалення, переміщення, зміна файлу, перейменування тощо)».
Межу задає не це рішення, а сканер: він читає **лише атрибути каталогу** — наявність, розмір, час
зміни, назву й розташування (жодного відкриття файлів, інакше кожен прохід на OneDrive
завантажував би всі заглушки з хмари). Отже:

**Помічається:** створення, видалення, зміна вмісту (змінюється розмір або `mtime`),
перейменування, переміщення між теками, ті самі події для тек, а також зміна, що прийшла з
першої теки на шлях, який уже чекає рішення (стає конфліктом).

**Не помічається — свідомо:**

| Що | Чому |
|----|------|
| Зміна вмісту, що зберегла і розмір, і `mtime` з точністю до 2 с | Виявити можна лише читанням усього файлу; на WAN це неприйнятно. Це те саме правило, за яким рушій працює сьогодні |
| Зміна атрибутів, прав доступу, власника, «лише читання» | Продукт їх не синхронізує взагалі (ні зараз, ні після цього етапу) |
| Файл, що виник і зник між проходами | Немає що погоджувати — стан не змінився |
| Тимчасові файли Office і подібні (`~$*`, `*.tmp`, `.~lock.*`) | Технічне сміття, відсікається до черги (§5.9) |
| Порожня тека, створена й лишена порожньою | Прохід її перенесе як звичайно — питати нема про що |

**Окремий випадок: перейменування, що змінило лише регістр** (`Звіт.docx` → `ЗВІТ.docx`). Для
Windows це той самий шлях, а первинний ключ бази порівнюється побайтово. Такий випадок
розпізнається окремою перевіркою в `MoveDetector` (однаковий шлях без урахування регістру, різний
побайтово) і показується як `renamed`; підтвердження виконується подвійним `Move` через тимчасове
ім'я — інакше Windows вважає операцію безпредметною.

### 5.5 Після рішення: як не спитати вдруге

| Рішення | Що записуємо в `entries` | Коли спитаємо знову |
|---------|--------------------------|---------------------|
| Підтверджено | обидва боки однакові, `Active` | при наступній зміні в B |
| Залишено як є (зміна) | обидва боки **як є зараз**, новий статус `Diverged` | коли B зміниться **ще раз** відносно записаного; зміна в A піддерева `Diverged` теж підіймає питання |
| Залишено як є (видалення) | `Tombstone` (існуючий статус, існуюча семантика) | якщо файл у B з'явиться знову |
| Залишено як є (додавання) | новий статус `LocalOnly` | якщо файл у B зміниться (розмір/час) |
| Повернуто | стан, як був до зміни, `Active` | при наступній зміні в B |

`Diverged` і `LocalOnly` — два нові значення `EntryStatus` (4 і 5). Значення додаються **в кінець**:
числа статусів лежать у базі, переставляння їх зіпсує наявні бази.

### 5.6 Версіонування (`.wfsversions`)

**Розташування.** Корінь модерованої теки (B) — там, де користувач її шукатиме. Тека створюється
прихованою, з `README.txt` усередині («це копії, які WorkFlowSync зберіг перед відкатом; можна
видалити»).

**Структура.** `\.wfsversions\<рррр-ММ-дд_ГГхвсс>\<відносний шлях>` — дзеркало дерева всередині
знімка за часом. Не `файл.дата.docx`: не ламає розширення, переживає кілька відкатів того самого
файлу, відкривається Провідником як звичайна тека.

**Що туди потрапляє — правило одне: версіонуємо лише те, чого не можна дістати ні з другого боку,
ні з Кошика.** Три випадки:

1. **відкат зміни або додавання** — копія B зникає за командою користувача;
2. **підтвердження видалення на корені без Кошика** (саме випадок замовника: Storage Box);
3. **перезапис файлу, який був змінений локально** — тобто програшний бік конфлікту.

І навпаки, **не** версіонуємо звичайне оновлення, коли локальна копія була недоторкана: вона
побайтово збігається з тим, що записано в стані, і той самий файл лишається в першій теці. Це
рішення тримає теку версій малою — інакше активна робоча тека подвоювала б записи на диск і
тягнула б це все в хмару.

Переміщення — це `Move`, там нічого не губиться, версія не потрібна.

**Невидимість для синхронізації.** Ім'я `.wfsversions` резервується в `TreeScanner` поруч із
перевіркою tombstone-тек: сканер не заходить туди **незалежно від списку виключень**. Те саме
для вже наявного `*.wfs-tmp`. Тест, що шукає `.wfsversions` у результаті сканування, — обов'язковий.

**Очищення — те, чого в запиті немає, але без чого функція з часом з'їсть диск (і трафік OneDrive).**
Налаштування «зберігати версії N днів» (типово 30) і «не більше N ГБ» (типово 5). Прибирання —
наприкінці проходу, цілими знімками (тека знімка або жива, або йде повністю), у Кошик. Виводиться
в журнал рядком `versions pruned=…`.

### 5.7 Перевірка перед застосуванням (позитивне підтвердження)

Між виявленням і рішенням минають хвилини або дні. Перед виконанням рішення обидва боки
перечитуються, і якщо реальність розійшлася із записом у черзі — рішення **не виконується**:

- B змінився ще раз → запис стає `stale`, на його місці з'являється новий `pending` із свіжими
  даними, у вікні — рядок «змінилося ще раз, перегляньте заново»;
- A змінився з моменту виявлення → запис стає `conflict`;
- A недоступний (мережа) → нічого не виконується, вікно показує «Перша тека недоступна», кнопки
  неактивні, черга чекає. Жодних часткових застосувань.

Це те саме правило, що вже рятує від застарілого скану в `SyncExecutor`, і воно тут потрібне ще
гостріше: тут між рішенням і дією стоїть людина.

### 5.8 Масовість: що буде, коли в теці видалять 10 000 файлів

Без окремої роботи вікно перетвориться на нечитабельний список, а «Підтвердити усі» — на одну
кнопку, що стирає піддерево на сервері назавжди. Потрібно:

1. **Групування за текою.** Однотипні події в одній теці згортаються в один рядок: «`\Палата 3` —
   видалено 240 файлів (1,2 ГБ)» з розкриттям. Групи будуються у view-model, дані лишаються
   порядковими.
2. **Стеля, як у `DeletionGuard`.** Понад 100 подій **і** понад 20% відомого про пару — черга
   приймається, але вікно відкривається з червоним попередженням «схоже на збій, а не на рішення»
   і «Підтвердити усі» вимкнене, доки користувач не зніме окремий запобіжник.
3. **Підтвердження гуртових дій** — окреме вікно з підсумком: скільки файлів, скільки байтів, куди
   саме («буде видалено у `\\сервер\шара\…`»), і що Кошика там немає. Для «Підтвердити усі» на
   видаленнях — ввести кількість або тримати клавішу? Достатньо явної кнопки з червоним акцентом і
   повним текстом наслідків.
4. **Стеля черги**: понад 20 000 відкритих записів — нові не додаються, у журналі `WARN`, у вікні
   «показано перші 20 000». Прохід не має падати через переповнення.

### 5.9 Спостерігач і частковий прохід

Погодження працює з **обома** джерелами змін, але з різними правами:

- **Повний прохід** виявляє все, включно з видаленнями.
- **Частковий прохід** (від спостерігача) сьогодні зобов'язаний відмовлятися від рішень, виведених
  з відсутності (§4.2 етапу 5). Тут заборона **послаблюється навмисно**: поставити запис у чергу —
  дія недеструктивна, а перед виконанням усе одно буде перевірка §5.7. Умова: тека, у якій зник
  об'єкт, існує і читається, і спрацьовує звичайна стеля (§5.8). Інакше — `DeferredToFullPass`.
  Без цього видалення в теці помічається лише раз на інтервал (до 30 хв), що для «погодження»
  відчувається як гальмування.
- **Відстрочка видалень і склейка перейменувань (§4.8 етапу 5) застосовується до постановки у
  чергу.** Інакше кожне збереження документа Word (створити tmp → видалити оригінал →
  перейменувати) породжуватиме два записи в черзі замість жодного. Вбудований список тимчасових
  шаблонів (`~$*`, `*.tmp`, `.~lock.*`) так само відсікається **до** черги.

### 5.10 Перше увімкнення: не залити користувача

Якщо ввімкнути погодження на парі, де боки вже розійшлися, перший же прохід видасть сотні записів
про зміни, яких користувач не робив «зараз». Тому вмикання пункту виконує **базовий прохід**:
поточний стан обох боків записується як погоджений (`Adopted`), у журнал іде
`approval baseline pair=… rows=…`, а черга починається з чистого аркуша. Діалог пари попереджає
про це одним рядком. Вимикання пункту — навпаки: усі відкриті записи треба вирішити або явно
скинути (діалог «лишилося N непогоджених змін: залишити все як є / повернути все / скасувати»).

### 5.11 Недоступна перша тека

Найчастіший стан у замовника — мережа є не завжди. Тому: черга наповнюється й показується завжди
(для цього потрібна лише друга, локальна тека), а **застосування** рішень вимагає першої теки. Якщо
її немає — рішення можна поставити «на чергу виконання» (`approved`, ще не виконано), і наступний
прохід із доступною мережею доводить справу до кінця з повторною перевіркою §5.7. Це дає користувачу
змогу розібрати чергу офлайн — ввечері, без VPN.

## 6. Інтерфейс

### 6.1 Вхід: банер у «Останніх змінах»

`RecentChangesViewModel` додатково рахує відкриті записи (`SELECT COUNT(*) … status = pending`) і
показує **над списком** смугу з іконкою-щитом: «Виявлено зміни, які потребують погодження — N».
Клік відкриває вікно погодження. Коли записів немає — смуги немає (не «0»).

Те саме число дублюється: підказкою на значку в треї, бейджем на картці пари в головному вікні й
рядком у «Журналі подій». Це стан, який користувач має помічати, не відкриваючи нічого спеціально.

### 6.2 Вікно «Погодження змін»

Звичайне вікно (не безрамкове спливаюче): 1000×640, змінюваного розміру, `CenterOwner`. Спливаюче
вікно останніх змін для цього не годиться — воно `Topmost`, без декорацій і зникає за кліком повз.

**Рядок** (три колонки + дії), точно за макетом замовника:

```
┌──────────────────────────┬──────┬──────────────────────────┬───────────────┐
│ Було                     │  →   │ Стало                    │  ✓   ⃠   ↺   │
│ Звіт.docx  2,1 МБ        │ ✎    │ Звіт.docx  2,4 МБ        │               │
│ \Палата 3\2026           │      │ \Палата 3\2026           │               │
└──────────────────────────┴──────┴──────────────────────────┴───────────────┘
```

- **видалено** — права колонка порожня, ліва підсвічена `Danger`/`DangerSoft`;
- **додано** — ліва колонка порожня, права підсвічена `Success`/`SuccessSoft`;
- **змінено** — обидві колонки, різниця розміру виділена (`+300 КБ` зеленим, `−1,2 МБ` червоним);
- **перейменовано/переміщено** — обидві колонки, відмінна частина шляху виділена;
- **конфлікт** — рамка `Warning`, третя дія в рядку («лишити версію з першої теки»).

Токени `Success`, `SuccessSoft`, `Danger`, `DangerSoft`, `Warning` у палітрі вже є — нових кольорів
не заводимо. Потрібні нові іконки в `Icons.axaml`: `IconFilePlus`, `IconFileMinus`, `IconFileEdit`,
`IconRename` (можна `IconArrowRight`), `IconUndo`, `IconX`, `IconShield`. Іконки-кнопки
обов'язково з `ToolTip.Tip` — кнопка без підпису й без підказки в вікні, де помилка коштує файлів,
неприйнятна.

**Підписи (пропозиція, замість дослівних із запиту).** «Скасувати» в рядку і «Скасувати» внизу
вікна — різні дії; це найнебезпечніша частина макета.

| У запиті | Пропоную | Підказка |
|----------|----------|----------|
| Підтвердити | **Підтвердити** ✓ | «Застосувати цю зміну й у першій теці» |
| Скасувати | **Залишити як є** ⃠ | «Нічого не змінювати; більше не питати про цю зміну» |
| Повернути | **Повернути** ↺ | «Повернути другу теку до попереднього стану» |
| Підтвердити усі | Підтвердити всі (N) | + вікно підсумку |
| Скасувати усі | Залишити всі як є (N) | |
| Повернути початковий стан | Повернути все (N) | + вікно підсумку |

**Ще потрібно, щоб вікном можна було користуватися:**

- **множинний вибір** з прапорцями і дії «для вибраних» — між «по одному» і «всі» зараз порожньо;
- **фільтр за типом і за парою** + пошук за назвою;
- **сортування**: за часом (типово), назвою, розміром, текою;
- **клавіатура**: ↑/↓ — рядок, `Enter` — підтвердити, `Backspace` — повернути, `Space` —
  вибір, `Ctrl+A`;
- **«Відкрити теку»** й **«Порівняти»** (відкрити обидва файли) у контекстному меню рядка;
- **вік події** («2 дні тому») — видно, що черга застоюється;
- стан порожнечі: «Непогоджених змін немає»;
- рядок-підсумок унизу: «Обрано 12 · буде скопійовано 340 МБ · буде видалено 4 файли».

**Поки вікно відкрите**, прохід може виявити нові зміни. Список **не перемальовується під руками**:
новий запис не має з'явитися між наведенням і кліком. Замість цього зверху виникає смуга
«Виявлено ще N змін — оновити», і список перечитується лише за кліком. Гуртові кнопки діють на те,
що зараз у списку, а їхнє вікно підсумку показує точну кількість на момент натискання.

### 6.3 Налаштування пари

У картці «ПРАВИЛА» діалогу пари, одразу під «Тип синхронізації», два рядки — обидва активні лише
для `twoWay` (за наявним зразком: вимикається контрол, а пояснення лишається читабельним):

```
Погодження змін   [✓] погоджувати зміни в другій теці
                  Зміни у «D:\OneDrive\…» не переносяться автоматично: програма
                  показує їх списком і чекає вашого рішення.

Версіонування     [✓] зберігати попередні версії у .wfsversions
                  Перед поверненням або видаленням копія лягає в приховану теку
                  всередині другої теки. Зберігати [30] днів, не більше [5] ГБ.
```

## 7. Конфігурація

`FolderPair` — плоскі властивості, як усі наявні:

```json
{
  "name": "Документи",
  "mode": "twoWay",
  "requireApproval": true,
  "approvalSide": "target",
  "versioning": true,
  "versionsPath": ".wfsversions",
  "versionsKeepDays": 30,
  "versionsMaxGb": 5
}
```

`approvalSide` і `versionsPath` пишуться завжди, хоч інтерфейс їх поки не показує (§13.1, §13.4):
поле в схемі коштує нічого, а його відсутність згодом означала б міграцію конфігів у всіх.

`SyncConfig.Validate()`:

- `requireApproval` на парі `mirror` — помилка конфігурації (як `autoClean` на `twoWay`);
- `versioning` без `requireApproval` — дозволено і корисно: випадки 2 і 3 з §5.6 (видалення на
  корені без Кошика, програшний бік конфлікту) працюють у будь-якій парі `twoWay`;
- `versionsPath` не може лежати всередині першої теки й не може збігатися з коренем пари;
- `versionsKeepDays` 1…3650, `versionsMaxGb` 1…1000.

Старі конфіги без цих полів читаються як `false` — поведінка не змінюється.

## 8. CLI

Резидентний режим може працювати без GUI (`wfs sync --loop`), тож черга має бути доступна з консолі:

```
wfs pending list   [--pair <назва>] [--json]
wfs pending approve  (--id <n> | --path <шлях> | --all) [--pair <назва>]
wfs pending dismiss  (--id <n> | --path <шлях> | --all) [--pair <назва>]
wfs pending revert   (--id <n> | --path <шлях> | --all) [--pair <назва>]
```

`--all` без `--pair` вимагає `--yes`. `wfs status` отримує рядок `pending=N` і ненульовий код
виходу за наявності черги — щоб Планувальник завдань міг це помітити.

## 9. Сповіщення і трей

- Поява **перших** непогоджених змін після порожньої черги — одне сповіщення «N змін чекають на
  погодження», клік відкриває вікно. Повторні — не частіше ніж раз на годину.
- Тихі години (F15) діють: це не аварія. Але значок у треї отримує **накладну крапку** й підказку
  «N змін чекають на погодження» — стан видно завжди, коли користувач подивиться на трей.
- `NotifyMode.Off` вимикає сповіщення, але не бейдж.

## 10. Тести

**Чисті (одиничні):**

- `MoveDetectorTests` — склейка, неоднозначність (два кандидати), нульові файли, тека;
- `ApprovalPlannerTests` — таблиця §5.4 і §5.5 повністю, заморозка теки й піддерева, конфлікт;
- `ApprovalStatusTests` — «залишити як є» не питає вдруге: три проходи поспіль дають 0 записів;
- `VersionPathTests` — побудова шляху знімка, колізії імен, довгі шляхи (>260);
- `VersionPruneTests` — очищення за днями і за обсягом, знімок або живий, або зникає цілком.

**Наскрізні (temp-теки):**

- видалення в B → прохід → запис у черзі, **на обох боках нічого не змінилося**;
- підтвердження → зникло в A; скасування → три проходи не змінюють нічого; повернення → B
  відновлено з A, копія лежить у `.wfsversions`;
- перейменування → один запис `renamed`, підтвердження — саме `Move`, а не копія;
- збереження файлу «як Word» (tmp → delete → rename) **не** створює жодного запису в черзі;
- зміна в A поверх замороженого шляху → `conflict`, файл B не затерто;
- `.wfsversions` не з'являється в результатах сканування ні з виключеннями, ні без них;
- недоступна перша тека: рішення приймаються, застосовуються наступним проходом;
- міграція бази v2→v3 зберігає всі рядки `entries`.

**GUI (view-model):** банер з'являється й зникає, групування, підрахунок підсумків, блокування
«Підтвердити всі» за стелею.

| **6.4** Версіонування | `.wfsversions` (резервування в сканері, запис, README, прихована тека), очищення за днями/обсягом, налаштування | 1,5 дня |

|-------|----------------|-----------|
| «Підтвердити всі» стирає піддерево на сервері | Кошика на Storage Box немає, відкату не існує | Стеля §5.8, вікно підсумку з повним шляхом, обов'язкова копія у `.wfsversions` при підтвердженні видалення на корені без Кошика |
| Черга застоюється, синхронізація тихо стоїть | Заморожені шляхи не синхронізуються з жодного боку | Вік події в рядку, бейдж у треї, `pending=N` у `status`, попередження в головному вікні, якщо є записи старші за 7 днів |
| Шум від Office і тимчасових файлів | Одне збереження = кілька подій ФС | Відстрочка видалень, склейка перейменувань і вбудовані шаблони застосовуються **до** черги (§5.9) |
| Хибне перейменування (склеїли не ті файли) | Підтвердження зробить `Move` не того файлу | Жорсткі умови §5.3, одноразова відповідність, показ обох шляхів у вікні перед рішенням |
| `.wfsversions` роздуває OneDrive | Тека лежить усередині синхронізованої з хмарою теки | Очищення за днями й обсягом, видно розмір у налаштуваннях, можливість винести теку поза ціль |
| Схема v3 і старий білд | `StateStore` навмисно відмовляється відкривати новішу базу | Згадати в примітках до випуску; `.v2-backup` перед міграцією |

## 13. Рішення, що потребують підтвердження замовника

Кожне питання має **рекомендовану відповідь** — саме її закладено в решту плану. Потрібне лише
«так» або зустрічне рішення; жодне з них не змінює обсяг більш ніж на пів дня, окрім 13.3.

### 13.1 Яку теку модеруємо → **другу (локальну, в OneDrive), жорстким правилом**

Перша тека — Storage Box через інтернет: доступна не завжди. Якби модерувалася вона, чергу не можна
було б ані наповнити, ані розібрати без мережі. Друга тека локальна — вона є завжди, і саме в ній
працює людина, тож «мої зміни, які я підтверджую перед тим, як вони підуть на спільний сервер» —
це рівно те, чого функція має досягати.

Вибір боку в діалозі **не робимо**: зайвий контрол, у якого один правильний стан. Але поле
`approvalSide` у конфігу пишеться одразу — якщо колись знадобиться, це буде рядок коду, а не
міграція конфігів.

### 13.2 Зміни в першій теці → **переносяться автоматично, як зараз**

Модерація обох боків перетворює синхронізацію на ручне злиття і подвоює чергу. Асиметрія тут не
недогляд, а точний розрахунок: **напрямок A→B зворотний, напрямок B→A — ні.** Усе, що прохід
робить у другій, локальній теці, лежить або в Кошику, або в `.wfsversions`, або лишається в першій
теці; те, що прохід зробить у першій теці, на Storage Box не повертається ніколи. Питати треба там,
де немає відкату.

Єдиний виняток уже закладено: зміна з A поверх шляху, що чекає рішення, не виконується мовчки, а
стає конфліктом (§5.2).

### 13.3 Версіонування поза відкатом → **так, але за правилом «лише невідновне»**

Не «кошик на кожен перезапис» (це подвоїло б записи на диск і вивантаження в OneDrive для активної
робочої теки), і не «лише при відкаті» (тоді програшний бік конфлікту зникає безслідно). Правило —
три випадки з §5.6: відкат, підтверджене видалення на корені без Кошика, і перезапис файлу, який
був змінений локально. Звичайне оновлення недоторканої копії не версіонується: вона побайтово
збігається зі станом, а оригінал лишається в першій теці.

Наслідок, який варто відзначити: `versioning` стає корисним і **без** погодження — це окремий
запобіжник для будь-якої двобічної пари.

### 13.4 Розташування `.wfsversions` → **усередині другої теки, як у запиті, але з полем `versionsPath`**

Тека версій потрібна людині в найгірший момент — коли файл уже зник. Тоді «відкрити робочу теку,
там `.wfsversions`» працює, а «десь поруч із `state.db` у теці програми» — ні. Те, що OneDrive
вивантажить її в хмару, при правилі 13.3 радше плюс: копія переживе й диск.

Запобіжники: прихована тека з `README.txt` усередині; очищення 30 днів / 5 ГБ; поточний розмір
видно прямо в налаштуваннях пари; поле `versionsPath` дозволяє однією правкою винести теку поза
OneDrive, якщо обсяг колись почне заважати.

### 13.5 «Залишити як є» для видаленого файлу → **назад не приносимо**

Це рівно семантика `tombstone`, з якою замовник уже живе в режимі дзеркала (правило F1: видалене
локально не повертається). Одна ментальна модель на весь продукт замість двох. Тихо відродити файл
через те, що хтось на сервері його торкнувся, означало б скасувати явне рішення користувача
непомітно для нього.

Щоб рішення не стало пасткою: у картці пари — лічильник «виключено рішенням: N» зі списком і
кнопкою «повернути в синхронізацію».

### 13.6 Автоматичне рішення за давністю → **ні, жодного автопідтвердження**

Будь-яка автовідповідь зводиться до одного з двох: «видалити на сервері, бо ніхто не відповів»
(незворотно) або «відкотити роботу користувача, бо ніхто не відповів» (втрата праці). Обидва
неприйнятні. Замість цього — щоб черга не застоялася непоміченою: вік події в рядку, попередження в
головному вікні для записів старших за 7 днів, крапка на значку в треї, `pending=N` і ненульовий
код виходу в `wfs status`.

### 13.7 Підписи кнопок → **так, заміна потрібна**

Остаточний набір (формулювання замовника збережені там, де вони однозначні):

| Місце | Підпис | Підказка |
|-------|--------|----------|
| Рядок | **Підтвердити** ✓ | Застосувати цю зміну й у першій теці |
| Рядок | **Залишити як є** ⃠ | Нічого не змінювати; більше не питати про цю зміну |
| Рядок | **Повернути** ↺ | Повернути другу теку до попереднього стану |
| Зверху | **Підтвердити всі (N)** | + вікно підсумку |
| Зверху | **Залишити всі як є (N)** | |
| Зверху | **Повернути початковий стан (N)** | + вікно підсумку |

Причина заміни одна: «Скасувати» в рядку означало б «залишити розбіжність», а «Скасувати» внизу
вікна — «закрити нічого не роблячи». Два значення одного слова в вікні, де ціна помилки — файли.
Гуртовий підпис «Повернути початковий стан» лишається дослівно: там двозначності немає.

# F1. Правила дзеркалювання

**Статус**: реалізовано (Етап 1, 2026-09-14) — `src/WorkFlowSync.Core/Planning/SyncPlanner.cs`; кожен рядок
таблиці покрито тестом у `tests/WorkFlowSync.Tests/SyncPlannerTests.cs`, наскрізні сценарії 1–6 — у `EndToEndTests`.

## Мета

Забезпечити три правила замовника для кожної пари «джерело → ціль»:

1. **Видалення в джерелі не впливає на ціль.** Локальна копія лишається.
2. **Додавання в джерелі додається в ціль.** Нові папки й файли копіюються; файли, які змінилися
   в джерелі і **не змінені локально**, оновлюються.
3. **Локальні дії не впливають на джерело і не скасовуються.** Що користувач видалив,
   перемістив або змінив локально — більше ніколи не підтягується заново з джерела.

Пара на паузі (`enabled: false`) не бере участі в автоматичних проходах — її стан просто
заморожується; ручний запуск цієї пари виконує всі правила як звичайно.

## Актори

- Джерело — відкривається **лише на читання**. Програма ніколи не пише в джерело.
- Ціль — локальна папка в OneDrive. Програма створює, оновлює й (за ретенцією) видаляє в Кошик
  лише ті об'єкти, які сама створила і які користувач не чіпав.

## Таблиця рішень

Для кожного відносного шляху `p` під час проходу відомо:
`S` — стан у джерелі (є/нема, size+mtime), `L` — стан у цілі (є/нема, size+mtime),
`DB` — запис у базі стану (нема / active / tombstone / local_modified).

| DB | S | L | Дія |
|----|---|---|-----|
| нема | є | нема | **Новий**: копіювати, записати `active`, `first_seen = now` |
| нема | є | є | Об'єкт з'явився локально сам (або дозаписаний FFS). Вважати наявним: записати `active` з `copied_* = фактичні L`; **не перезаписувати** (правило 3), якщо `S ≠ L` — позначити `local_modified` |
| нема | нема | є | Локальний сторонній об'єкт. Ігнорувати, у базу не писати |
| active | є | є, `L == copied` | Локально не чіпали. Якщо `S ≠ copied` → **оновити** копію і `copied_*` |
| active | є | є, `L ≠ copied` | Користувач змінив локально → `local_modified`. Джерело ігнорується надалі |
| active | є | нема | Користувач видалив/перемістив → `tombstone`. Не копіювати знову |
| active | нема | є | Видалено в джерелі → **нічого** (правило 1). Запис лишається `active` (щоб повернення файлу в джерело було оновленням, а не «новим») |
| active | нема | нема | Зникло з обох боків → `tombstone` (щоб повторна поява в джерелі не відновила те, що користувач прибрав) |
| tombstone | будь-що | будь-що | **Нічого**. Навіть якщо в джерелі з'явився файл з тим самим шляхом |
| local_modified | будь-що | будь-що | **Нічого** з боку джерела. Якщо L зникло → `tombstone` |

Для **папок** правила ті самі; папка порівнюється лише за наявністю. Видалена локально папка
стає `tombstone` для себе і для всіх нащадків (їх окремі записи теж переводяться в `tombstone`),
тому нові файли в цій папці в джерелі більше не з'являються локально.

## Порівняння файлів

`S ≠ L` означає розбіжність **розміру або mtime** (з точністю до 2 с — FAT/SMB-округлення
і DST-зсуви враховуються як у FFS `TimeAndSize`). Вміст не хешується.

При копіюванні зберігається mtime джерела (як `File.Copy` на Windows); `copied_mtime` і
`copied_size` читаються з цілі **після** копіювання, а не беруться з джерела, щоб порівняння
далі було «яблука з яблуками».

## Сценарії приймання

1. У джерелі з'явився `2026\звіт.docx` → після проходу він є в цілі, у базі `active`.
2. Файл із п.1 видалено в джерелі → після проходу він досі є в цілі.
3. Файл із п.1 користувач видалив локально → після проходу його нема; у базі `tombstone`; після
   ще одного проходу його все ще нема, хоча в джерелі він є.
4. Файл із п.1 користувач відредагував локально; у джерелі його теж оновили → локальна версія
   збережена; база `local_modified`.
5. Користувач перемістив локально папку `2025_рік` в архів → усі її нащадки `tombstone`; нові
   файли в `2025_рік` у джерелі більше не копіюються.
6. Джерело недоступне (VPN вимкнено) → прохід пропущено із записом у лог; у базі жодних змін.

## Відкриті питання

- Чи потрібно колись «розтомбстонити» шлях вручну (наприклад, користувач передумав)? Пропозиція:
  команда `forget <шлях>` на Етапі 2 — видаляє запис, і об'єкт з'явиться як новий.

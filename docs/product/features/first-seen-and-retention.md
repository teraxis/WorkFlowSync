# F3. Дата появи (`first_seen`) і ретенція

**Статус**: `first_seen` і backfill реалізовано (Етап 1); ретенція — Етап 2.
Рішення замовника 2026-09-14: backfill = `min(ctime, mtime)`, автоматично на першому проході пари.

## Мета

1. Фіксувати для кожного об'єкта **момент появи в джерелі** — коли сканер уперше його побачив.
   Це не дата створення і не дата зміни файлу (вони можуть бути будь-якими: скопійований старий
   документ має ctime «сьогодні», а mtime — п'ятирічної давнини).
2. Дати змогу задати для пари вікно зберігання, наприклад «1 рік»: у локальному дзеркалі
   лишаються лише об'єкти, що з'явилися не раніше ніж рік тому.

## `first_seen`

- Встановлюється один раз, при створенні запису, значенням `now (UTC)`.
- Ніколи не змінюється: ні при оновленні файлу, ні при переході між статусами.
- Для папки — момент першої появи папки; для файлів у ній — їхні власні моменти.
- Роздільна здатність — час проходу. Якщо інтервал 30 хв, похибка ≤ 30 хв. Достатньо для
  ретенції в днях.

### Перший прохід (backfill)

На першому проході всі наявні об'єкти отримали б `first_seen = сьогодні`, і ретенція «1 рік»
запрацювала б лише через рік. Тому для об'єктів, яких нема в базі і **база порожня** (або
ввімкнено `--backfill`), `first_seen = min(ctime, mtime)` файлу в джерелі як наближення.
Погоджено 2026-09-14. Реалізовано в `SyncPlanner` (`backfillFirstSeen`): часи до 1990 року або в
майбутньому відкидаються на користь `now`.

## Ретенція

Параметр пари `retention` (TimeSpan, наприклад `365.00:00:00`); `null` = зберігати вічно.

Правило: наприкінці кожного проходу для записів `active` з `first_seen < now − retention`:

1. Локальний об'єкт переміщується в **Кошик** (не видаляється безповоротно).
2. Запис переводиться в `tombstone` (`status_changed = now`), тому об'єкт **не повернеться**
   з джерела, доки там існує (правило 3 діє і тут).
3. Папка видаляється в Кошик лише якщо після видалення файлів вона порожня; непорожня (є
   `local_modified` або сторонні локальні файли) — лишається, у лог іде попередження.

Ретенція **не** торкається `local_modified` (користувач працював з файлом — його рішення) і
сторонніх локальних об'єктів (їх нема в базі).

Кошик: `Microsoft.VisualBasic.FileIO.FileSystem.DeleteFile(..., RecycleOption.SendToRecycleBin)`
або `SHFileOperation` через P/Invoke — обидва працюють від звичайного користувача. OneDrive
при цьому бачить звичайне видалення і теж кладе файл у свій «Кошик OneDrive».

## Конфігурація (див. F6)

```json
{ "name": "vrp", "source": "E:\\vrp", "target": "D:\\OneDrive\\Робоча папка", "retention": "365.00:00:00" }
```

Зміна `retention` на менше значення застосується на наступному проході до всіх старих записів
одразу — це може прибрати багато файлів. `--dry-run` показує список до виконання.

## Сценарії приймання

1. Файл з'явився в джерелі 2025-01-10; `retention = 365 днів`; прохід 2026-01-11 → файл у Кошику,
   запис `tombstone`; наступний прохід — файл не повертається, хоч у джерелі є.
2. Той самий файл користувач редагував локально 2025-06-01 (`local_modified`) → ретенція його
   не чіпає.
3. `retention` не задано → жоден файл не видаляється незалежно від давності.
4. `--dry-run` перелічує кандидатів на видалення, нічого не рухаючи.

## Відкриті питання

- Чи потрібне окреме вікно для папок (видаляти порожні папки старші за N)? Пропозиція: ні,
  папки живуть, поки в них щось є.

# F3. Дата появи (`first_seen`) і ретенція

**Статус**: реалізовано повністю (Етап 2, 2026-09-14) — `SyncPlanner.ApplyRetention`, `RecycleBin` (SHFileOperation),
тести `RetentionTests` + e2e `Retention_recycles_expired_files_and_empty_folders_and_never_brings_them_back`.
Рішення замовника 2026-09-14: backfill = `min(ctime, mtime)`, автоматично на першому проході пари.

## Мета

1. Фіксувати для кожного об'єкта **момент появи в джерелі** — коли сканер уперше його побачив.
   Це не дата створення і не дата зміни файлу (вони можуть бути будь-якими: скопійований старий
   документ має ctime «сьогодні», а mtime — п'ятирічної давнини).
2. Дати змогу задати для пари вікно зберігання, наприклад «1 рік»: у локальному дзеркалі
   лишаються лише об'єкти, що з'явилися не раніше ніж рік тому.

## `first_seen`

- Встановлюється один раз, при створенні запису, значенням `now (UTC)`.
- Ніколи не змінюється: ні при оновленні файлу, ні при переході між статусами.
- Для папки — момент першої появи папки; для файлів у ній — їхні власні моменти.
- Роздільна здатність — час проходу. Якщо інтервал 30 хв, похибка ≤ 30 хв. Достатньо для
  ретенції в днях.

### Перший прохід (backfill)

На першому проході всі наявні об'єкти отримали б `first_seen = сьогодні`, і ретенція «1 рік»
запрацювала б лише через рік. Тому для об'єктів, яких нема в базі і **база порожня** (або
ввімкнено `--backfill`), `first_seen = min(ctime, mtime)` файлу в джерелі як наближення.
Погоджено 2026-09-14. Реалізовано в `SyncPlanner` (`backfillFirstSeen`): часи до 1990 року або в
майбутньому відкидаються на користь `now`.

## Ретенція

Параметр пари `retention` (TimeSpan, наприклад `365.00:00:00`); `null` = зберігати вічно.

Правило (уточнено при реалізації): наприкінці кожного проходу для **файлів** `active` з
`first_seen < now − retention`, локальна копія яких ціла (`L == copied`):

1. Локальний файл переміщується в **Кошик** (не видаляється безповоротно). Ретенція має пріоритет
   над оновленням: якщо джерело змінило прострочений файл, він усе одно йде в Кошик.
2. Запис переводиться в `tombstone` (`status_changed = now`), тому файл **не повернеться**
   з джерела, доки там існує (правило 3 діє і тут).
3. **Папки самі по собі не старіють.** Інакше нова доповідь, покладена в стару папку «2024»,
   ніколи не з'явилася б локально. Папка, у якій після ретенції не лишилося нічого (ні наших
   файлів, ні `local_modified`, ні сторонніх локальних), теж іде в Кошик, а її запис
   **видаляється** (не tombstone): щойно в джерелі в ній з'явиться новий файл — папка повернеться
   разом із ним. Обробка знизу вгору (найглибші першими). Якщо на момент виконання папка вже не
   порожня — лишається з попередженням у лозі.

Ретенція **не** торкається `local_modified` (користувач працював з файлом — його рішення),
файлів, змінених локально саме зараз (вони стають `local_modified`), і сторонніх локальних
об'єктів (їх нема в базі).

Кошик: `SHFileOperationW` (FO_DELETE + FOF_ALLOWUNDO, без UI) через P/Invoke —
`Core/Execution/RecycleBin.cs`; працює від звичайного користувача. Грабля: `Pack = 1` для
`SHFILEOPSTRUCT` лише на x86, на x64 дає AccessViolation. OneDrive бачить звичайне видалення
і теж кладе файл у свій «Кошик OneDrive».

Порядок на першому проході: прострочений файл, якого ще нема локально, **спершу копіюється**
(він «новий» для нас), а в Кошик іде на наступному проході — коли вже є `active`-рядком. Щоб
не тягнути гігабайти старого архіву лише для того, щоб одразу викинути, задавайте `retention`
до першого проходу і перевіряйте `--dry-run`: план покаже `new=` для таких файлів. (Можливе
поліпшення — не копіювати вже прострочене; поки не реалізовано, див. відкриті питання.)

## Конфігурація (див. F6)

```json
{ "name": "vrp", "source": "E:\\vrp", "target": "D:\\OneDrive\\Робоча папка", "retention": "365.00:00:00" }
```

Зміна `retention` на менше значення застосується на наступному проході до всіх старих записів
одразу — це може прибрати багато файлів. `--dry-run` показує список до виконання.

## Сценарії приймання

1. Файл з'явився в джерелі 2025-01-10; `retention = 365 днів`; прохід 2026-01-11 → файл у Кошику,
   запис `tombstone`; наступний прохід — файл не повертається, хоч у джерелі є.
2. Той самий файл користувач редагував локально 2025-06-01 (`local_modified`) → ретенція його
   не чіпає.
3. `retention` не задано → жоден файл не видаляється незалежно від давності.
4. `--dry-run` перелічує кандидатів на видалення, нічого не рухаючи.

## Відкриті питання

- ~~Окреме вікно для папок~~ — вирішено: папки не старіють, порожні прибираються й забуваються.
- Не копіювати на першому проході файли, які за backfill уже прострочені (одразу tombstone без
  копії)? Економить трафік на старих архівах; ризик — розбіжність із FFS-дзеркалом. Пропозиція:
  опція пари `skipExpiredOnFirstPass`, за замовчуванням вимкнена.

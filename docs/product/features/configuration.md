# F6. Конфігурація

**Статус**: затверджено; парсер і валідація реалізовані (Етап 0) —
`src/WorkFlowSync.Core/Config/SyncConfig.cs`. Приклад: `config.example.json`.

## Файл

**Портативне розміщення (вимога замовника 2026-09-15): усі файли програми — `config.json`, `state.db`,
`logs\` — зберігаються в папці, з якої запущено `WorkFlowSync.exe` / `wfs.exe`.** Робоча тека
процесу (CWD) не має значення: шлях береться від розташування exe (`AppContext.BaseDirectory`),
тож і Планувальник із CWD = System32, і ярлик автозапуску знаходять ті самі файли. На першому
запуску GUI одразу створює `config.json` із типовими значеннями, щоб папка була «повною».

`config.json` поруч з exe (або `--config <шлях>` для тестів). JSON з коментарями `//` і кінцевими
комами. Кодування UTF-8. Відносні `statePath`/`logPath` — від папки конфігу; на сторінці
«Налаштування → Файли програми» показано папку програми, кнопку «Відкрити» і розв'язані абсолютні
шляхи бази й логів.

```json
{
  "pairs": [
    {
      "name": "vrp",
      "mode": "mirror",
      "source": "E:\\vrp",
      "target": "D:\\OneDrive\\Робоча папка",
      "links": "follow",
      "maxAge": "365.00:00:00",
      "autoClean": null,
      "exclude": [ "\\Друга дисциплінарна палата\\*Робочий.docx" ]
    }
  ],
  "statePath": "state.db",
  "logPath": "logs",
  "logKeepDays": 30,
  "interval": "00:30:00",
  "scanParallelism": 8,
  "scanBufferSize": 262144
}
```

## Поля

| Поле | Тип | За замовчуванням | Опис |
|------|-----|------------------|------|
| `pairs[]` | масив | — | обов'язково ≥ 1 |
| `pairs[].name` | рядок | — | стабільний ключ пари в базі стану; **перейменування осиротить записи** |
| `pairs[].enabled` | так/ні | `true` | стан пари: `true` — «виконується» (перевіряється автоматично кожні `interval`), `false` — пауза. Ручний запуск (кнопка **Перевірити зараз** або `wfs sync --pair`) працює в обох станах. Пишеться самою програмою при натисканні ▶/⏸ |
| `pairs[].source` | шлях | — | корінь джерела (UNC або підключений диск); лише читання |
| `pairs[].target` | шлях | — | корінь локального дзеркала |
| `pairs[].mode` | `mirror` / `twoWay` | `mirror` | F13: дзеркало в один бік або повна синхронізація в обидва |
| `pairs[].links` | `follow` / `skip` / `recreate` | `follow` | F4 |
| `pairs[].interval` | TimeSpan / null | null (= `interval`) | F7: власний період перевірки цієї пари. `null` = загальний `interval`. Мінімум 1 хв. Кожна пара має власний розклад: робоча тека, що змінюється щохвилини, і архів на 50 тис. тек, який сканується хвилинами, не повинні перевірятися разом |
| `pairs[].watch` | `auto` / `on` / `off` | `auto` | F14: чи реагувати на зміни одразу, чи лише за `interval`. `auto` — вирішувати за типом сховища. Перевірка за інтервалом працює в будь-якому разі, тож стеження саме по собі нічого не ламає. Відсутнє поле в старих конфігах читається як `auto` |
| `pairs[].cloudFiles` | `skip` / `hydrate` | `skip` | F13: що робити з файлами, які лежать лише в хмарі (OneDrive Files On-Demand), коли їх треба скопіювати на другий бік. `skip` — не копіювати й попередити в журналі; `hydrate` — завантажити з хмари. Діє лише в режимі `twoWay` |
| `pairs[].maxAge` | TimeSpan / null | null (будь-якої давності) | F3: переносити лише те, що зʼявилося за останні N. Старіше лишається в джерелі й не копіюється; з локальної теки не видаляє нічого. Формат `d.hh:mm:ss`; лише `mirror` |
| `pairs[].autoClean` | TimeSpan / null | null (вимкнено) | F3: переносити в Кошик наші копії, додані понад N тому. Вік — за нашою датою появи. У джерелі не зникає нічого. Лише `mirror`: на парі `twoWay` конфіг відхиляється |
| `pairs[].retention` | TimeSpan / null | — | застаріле (до 2026-09-17). Читається як `maxAge` і назад не записується |
| `pairs[].exclude[]` | шаблони | `[]` | відносно кореня джерела; синтаксис FFS: `\папка\*.docx`, `*\~$*` |
| `statePath` | шлях | `state.db` | F2 |
| `logPath` | папка | `logs` | F8 |
| `logKeepDays` | 1..3650 | 30 | F8: скільки днів зберігати `wfs-*.log`; старіші видаляються при наступному проході. У GUI — «Налаштування → Файли програми → Зберігати журнали» |
| `notifications` | `all` / `errorsOnly` / `off` | `all` | F10: чи показувати повідомлення після проходу. `all` — нові файли й проблеми; `errorsOnly` — лише проблеми; `off` — нічого |
| `quietHoursFrom` / `quietHoursTo` | 0..23 | `0` / `0` | F10: години, коли буденні повідомлення притримуються (проблеми показуються завжди). Однакові значення = тихих годин немає; діапазон може переходити через північ (`22` → `8`) |
| `interval` | TimeSpan | `00:30:00` | **більше не налаштовується у вікні** (з 2026-09-16 розклад у кожної пари свій). Лишається як: запасне значення для пар без власного `interval` (старі конфіги), і період завдання Планувальника — туди пишеться **найменший** з інтервалів пар, бо завдання одне на всіх. Мінімум 1 хв |

| `scanParallelism` | 1..64 | 8 | F5: верхня межа паралельних листингів; `cpuLoad` може її знизити |
| `cpuLoad` | `balanced` / `full` / `low` | `balanced` | F5: скільки машини дозволено зайняти проходу (паралелізм + пріоритет потоків і процесу) |
| `scanBufferSize` | ≥ 4096 | 262144 | F5 |

## Виключення

Синтаксис сумісний із FreeFileSync (список можна перенести вручну як є): шлях відносно
кореня джерела з провідним `\`; `*` і `?`; шаблон без `\` на початку збігається в будь-якій
папці. Порівняння без урахування регістру. Виключений об'єкт у базу не потрапляє. Виключення
застосовуються до сканера (в папку-виключення не спускаємось).

## Валідація

`wfs config validate` виводить пари і проблеми; код виходу 2 при помилках.
Перевірки: є пари; імена непорожні й унікальні; source/target непорожні; maxAge > 0; autoClean > 0 і лише для `mirror`;
interval ≥ 1 хв; parallelism 1..64; buffer ≥ 4096. Етап 1 додасть: target не всередині source
і навпаки; пари не перетинаються цілями.

## Сценарії приймання

1. `config validate` на `config.example.json` → `config: OK`, код 0 (виконано в Етапі 0).
2. Дві пари з іменем `vrp`/`VRP` → повідомлення про дублікат, код 2 (тест є).

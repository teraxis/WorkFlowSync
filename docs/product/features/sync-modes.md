# F13. Типи синхронізації пари

**Статус**: реалізовано (2026-09-15) — `src/WorkFlowSync.Core/Config/SyncMode.cs`,
`src/WorkFlowSync.Core/Planning/TwoWayPlanner.cs`; тести — `tests/WorkFlowSync.Tests/TwoWayTests.cs`.

## Мета

Пара папок може працювати у двох режимах. Тип обирається в налаштуваннях пари
(«Папки → ⋯ → Редагувати… → ПРАВИЛА → Тип синхронізації») і видно просто в картці пари:
іконка між двома шляхами — **→** для дзеркала, **⇄** для повної синхронізації.

| Режим | `mode` у config.json | Значок | Що робить |
|-------|----------------------|--------|-----------|
| Дзеркало (в один бік) | `mirror` (типово) | → | Правила замовника F1: нове з джерела копіюється; видалене в джерелі лишається у вас; видалене, переміщене чи змінене локально назад не повертається |
| Повна синхронізація (в обидва боки) | `twoWay` | ⇄ | Усе, що стається в одній папці, стається і в іншій: створення, зміни **і видалення** |

Режим дзеркала — це рівно те, що було до 2026-09-15; наявні пари читаються як `mirror`.

## Повна синхронізація: правила

Обидві папки рівноправні, тож термін «джерело/ціль» тут умовний (у діалозі вони підписані
«Перша папка» / «Друга папка»). Рішення для кожного шляху:

| Що бачимо | Дія |
|-----------|-----|
| Є лише в одній папці, у базі запису немає | **Новий** → скопіювати в іншу папку |
| Є в обох, файли однакові | Нічого; записати обидві сторони в базу |
| Є в обох, змінився з одного боку | Оновити другий бік |
| Є в обох, змінився з обох боків | **Конфлікт**: перемагає новіший `mtime`, у журналі — `WARN` |
| Був у базі, зник з одного боку | **Видалити** другу копію (у Кошик) і забути запис |
| Зник з одного боку, але з другого був змінений | Зміна важливіша: копію повертають назад, у журналі — `WARN` |
| Зник з обох боків | Просто забути запис |
| Папку видалено з одного боку, але в неї надійшов новий вміст | Папку **не** видаляють (щоб було куди покласти нове) |

Порядок дій у проході: спочатку створення й оновлення (батьки раніше за дітей), потім видалення
(найглибші раніше). Видалення завжди йде **в Кошик** — ніколи `File.Delete`.

Стан зберігається в тій самій таблиці `entries`: `src_size`/`src_mtime` описують першу папку,
`copied_size`/`copied_mtime` — другу, тож окремої схеми для режиму не потрібно. Статуси
`tombstone` і `local_modified` у цьому режимі не використовуються.

**Що не діє в повній синхронізації:**

- правила F1 про «видалене локально не повертається» — тут видалення навпаки переноситься;
- строк зберігання (F3): поле в діалозі неактивне, а якщо `retention` лишилося в config.json
  від попереднього режиму — воно ігнорується, з попередженням у журналі.

Виключення (F6) діють з обох боків: виключений шаблон не копіюється в жодному напрямку.
Лінки (F4) обробляються однаково для обох папок.

## Пара «в собі»

Пара, у якої обидва шляхи — та сама папка, або один шлях лежить усередині іншого, відхиляється:
кожен прохід копіював би копію. Перевірка є і в діалозі пари (повідомлення українською), і в
`SyncConfig.Validate()` — тобто вручну відредагований `config.json` теж не пройде
(`wfs config validate`, і фоновий цикл пропустить такий прохід).

Сусідні папки зі спільним префіксом (`D:\Work` і `D:\Work-2`) — нормальна пара.

## Обидві папки локальні

Ані режим, ані решта коду не знають про «мережевість»: `D:\Робоче` → `E:\Backup` працює так само,
як UNC → OneDrive. Мережеві шляхи лише повільніші, тому для них важливі налаштування сканера (F5).

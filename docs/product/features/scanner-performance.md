# F5. Сканер: продуктивність на великих деревах

**Статус**: реалізовано (Етап 1) — `src/WorkFlowSync.Core/Scanning/TreeScanner.cs`.
Замір 2026-09-14 (локальний NVMe, `C:\Program Files`, 8 воркерів, буфер 256 КБ): 20 335 папок /
206 497 файлів / 7 лінків — **1,8 с** холодний кеш, **0,8 с** теплий. SMB-замір — після наповнення тестової пари.

## Мета

Повний прохід джерела з сотнями тисяч файлів по SMB за десятки секунд, з інтервалом 30 хв —
без агента на сервері, без прав адміністратора, без USN-журналу (недоступний по мережі; локально
потребує адміністратора).

## Принцип

Над SMB коштує не файл, а **виклик**. Один `NtQueryDirectoryFile` повертає імена, розміри,
атрибути й часи всіх дітей папки — все, що потрібно для порівняння `size + mtime`. Тому вартість
проходу має бути **O(папок)**, а не O(файлів).

## Вимоги

1. **Великий буфер листингу.** `EnumerationOptions.BufferSize` (конфіг `scanBufferSize`,
   за замовчуванням 256 КБ; типово 4 КБ ⇒ ~50 round-trip'ів на папку з 1000 файлів). Це
   найбільший одиничний виграш і причина, чому .NET тут кращий за Go/Rust (там буфер не
   регулюється).
2. **Жодних викликів «на файл».** Тільки дані з листингу. `FileSystemEnumerable<T>` віддає
   `ref struct FileSystemEntry` — без алокації `FileInfo` на запис. Заборонено: `File.Exists`,
   `FileInfo.Length`, `GetLastWriteTime` окремо для кожного файлу.
3. **`AttributesToSkip = 0`.** Стандартні `EnumerationOptions` мовчки пропускають Hidden/System.
   FFS такі файли копіює — ми теж.
4. **Власна рекурсія**, не `RecurseSubdirectories = true`: контроль reparse point'ів (F4),
   пропуск `tombstone`-папок (F2), виключень (F6), паралелізм.
5. **Паралельний обхід**: черга папок + N воркерів (`scanParallelism`, за замовчуванням 8,
   діапазон 1..64). SMB добре масштабується на кілька одночасних запитів.
6. **Без хешування.** Порівняння лише за `size + mtime` з допуском 2 с.
7. **Ціль (локальний NTFS)** сканується тим самим сканером — читання атрибутів не гідратує
   OneDrive-заглушки. Розмір заглушки в листингу = логічний розмір файлу, mtime збережено —
   порівняння з `copied_*` коректне.
8. **Швидкий шлях за mtime папки** (опційно, Етап 2): NTFS оновлює mtime папки при
   додаванні/видаленні/перейменуванні прямих дітей. Це фільтр для пошуку *нових* об'єктів, але
   не для *оновлених* файлів; оскільки листинг дешевий (п.1), використовувати лише як
   оптимізацію, не як основу.
9. **FileSystemWatcher по SMB** — лише як тригер «проскануй раніше», не як джерело правди
   (губить події, залежить від сервера). Не в базовому обсязі.

## Орієнтири

LAN, round-trip ~0,5 мс, 8–16 воркерів → 1–3 тис. папок/с. Дерево 50 тис. папок / 500 тис.
файлів → 20–60 с. Це має бути виміряно на реальному джерелі на Етапі 1 і записано в
`docs/architecture.md` (Рішення).

## Вимірювання

`sync --once` пише в лог: кількість папок/файлів, тривалість сканування джерела, цілі, планування,
виконання; байти скопійовано. `status` показує останні значення.

## Сценарії приймання

1. На тестовому дереві (10 тис. папок, 100 тис. файлів, локально) прохід без змін < 5 с.
2. Збільшення `scanBufferSize` з 4 КБ до 256 КБ на SMB-джерелі зменшує час сканування щонайменше
   вдвічі (зафіксувати вимір).
3. Профіль проходу: нуль викликів `GetFileAttributes`/`FindFirstFile` на окремі файли
   (перевірка через Process Monitor).

# F7. CLI, режими запуску, автозапуск

**Статус**: реалізовано повністю (Етап 3, 2026-09-14) — `src/WorkFlowSync.Cli/Program.cs`, `Core/LoopRunner.cs`,
`Core/PassLock.cs`, `Core/Autostart.cs`; тести `ResidentModeTests`.
Консольний файл — **`wfs.exe`**; графічний — `WorkFlowSync.exe` (F11). Обидва читають той самий `config.json`.
`sync`, `status`, `forget` — Етапи 1–2 (`import-excludes` вилучено 2026-09-15, F9); `--loop`, автозапуск — Етап 3.

## Команди

```
wfs sync [--once | --loop] [--config <path>] [--dry-run]
wfs status [--config <path>]
wfs probe <path> [--watch <seconds>]
wfs config validate [--config <path>]
wfs forget <relative-path> [--pair <name>] [--config <path>]
wfs version
```

| Команда | Дія |
|---------|-----|
| `sync --once` | один прохід усіх **увімкнених** пар і вихід (за замовчуванням). Режим для Планувальника завдань. Реалізовано |
| `sync --pair <name>` | прохід лише однієї пари, навіть якщо вона на паузі |
| `sync --pair <name> --scope <шлях>` | прохід лише по одній теці пари (шлях відносно її кореня) — **лише додавання й оновлення**, жодних видалень, tombstone чи ретенції (F1, «Частковий прохід»). Потребує рівно однієї пари; з `--loop` не поєднується. Це той самий механізм, яким користуватиметься реакція на зміни |
| `sync --backfill` | брати `first_seen = min(ctime, mtime)` навіть коли база пари вже не порожня |
| `sync --verbose` | DEBUG-рядки в лог |
| `sync --loop` | резидент. **Кожна пара має власний розклад** (2026-09-16): цикл щоразу визначає, чия черга настала, і перевіряє лише її; сон розраховується до найближчого дедлайну. Пари, у яких немає власного `interval`, користуються загальним. Коли настала черга всіх одразу (звичайний випадок після старту) — це один прохід, який відкриває базу стану один раз, а не по разу на пару. Якщо всі пари на паузі, цикл **не робить порожніх проходів** узагалі. Далі: прохід, сон `interval`, знову. **Конфіг перечитується перед кожним проходом** (зміни з GUI діють без перезапуску); невалідний конфіг — прохід пропускається з ERROR; помилка проходу не зупиняє цикл; зайнятий замок — пропуск з WARN. Ctrl+C зупиняє між проходами або перериває поточний (стан перерваного не пишеться) |
| `sync --dry-run` | розрахувати й вивести дії, нічого не змінювати (ні файлів, ні бази) |
| `status` | лічильники стану за парами, час і результат останнього проходу, розмір бази |
| `probe <шлях>` | діагностика одного кореня: тип носія (локальний / знімний / мережевий у LAN / віддалений), розгорнутий UNC для підключеної літери, адреса хоста, час першого запису лістингу (≈ один round-trip) і час лістингу кореня, а також рекомендоване джерело змін. **Лише читання** — у корені нічого не створюється й не змінюється |
| `probe <шлях> --watch <сек>` | додатково слухає сповіщення про зміни вказану кількість секунд і друкує їх. Потрібно, щоб з'ясувати, чи взагалі працює notify на конкретній шарі. Якщо за час прослуховування ніхто нічого не змінив, результат так і звітується — «inconclusive», а не «не працює» |
| `autostart on\|off\|status [--tray]` | ярлик у папці автозавантаження: без `--tray` → `wfs sync --loop` (фоновий процес без вікна), з `--tray` → `WorkFlowSync.exe --tray` (значок біля годинника, F10) |
| `task on\|off\|status` | завдання Планувальника `WorkFlowSync` → `wfs sync --once` кожні `interval` хв; від поточного користувача, лише коли увійшов, без `/RL HIGHEST` |
| `config validate` | F6 |
| `forget <шлях>` | забути запис(и) стану — F9 (реалізовано) |

Коди виходу: `0` ок; `1` помилка виконання; `2` помилка використання/конфігу; `3` не реалізовано;
`4` інший прохід уже виконується для цього конфігу. Для `probe` код `1` означає «корінь недоступний».
Консоль і лог — UTF-8.

## Діагностика кореня (`probe`)

Реалізовано 2026-09-15 (`Core/RootProbe.cs`), тести — `RootProbeTests`. Відповідає на питання
«що це за папка і чого від неї очікувати», перш ніж вмикати для неї відстеження змін.

```
> wfs probe S:\
root: S:\
  kind:         RemoteShare
  drive type:   Network
  unc:          \\<host>\<share>
  host:         <host> -> 91.98.240.208 (public)
  available:    yes
  first entry:  169,8 ms   (roughly one round trip)
  root listing: 80,5 ms for 25 entries
  change source: IntervalScan (run with --watch to find out whether notifications work at all)
```

Тип визначається так: підключена літера розгортається в UNC через `WNetGetConnection`, хост
резолвиться в адресу, і **приватна адреса** (RFC 1918, link-local, CGNAT, unique local) означає
локальну мережу. Якщо адресу не вдалося дізнатися, вирішує **затримка**: менше 10 мс на перший
запис лістингу — локальна мережа, більше — інтернет. Приватна адреса сильніша за затримку, щоб
LAN-шара за повільним VPN не була помилково визнана віддаленою.

Замір проходу тепер теж є в журналі: рядок `pass end` містить `cpu=` (процесорний час проходу і
його частка від загального), `rss=` (робочий набір процесу) і `alloc=` (скільки пам'яті виділено
за прохід). Це дає числа для рішення, чи є сенс у оптимізаціях представлення даних.

## Один екземпляр

Замків два, і вони різні за призначенням.

### Одне вікно на конфіг (`SingleInstance`, 2026-09-15)

`WorkFlowSync.exe` перевіряє це **до старту Avalonia**, тож повторний запуск нічого не малює на
екрані: він миттєво завершується з кодом `0` і просить копію, яка вже працює, показати своє вікно
(іменована подія `Local\WorkFlowSync.show.<hash>`). Для користувача це виглядає як «клацнув ярлик —
відкрилося вже запущене вікно», а не як друга програма.

Замок тримається **весь час життя процесу** і прив'язаний до шляху `config.json`, а не до
комп'ютера: продукт портативний, тож дві папки зі своїми `config.json` — це дві незалежні
установки, і вони мають працювати одночасно. Заборонено саме **два запуски однієї папки**: інакше
обидві копії ганяли б проходи по одній базі стану, блокуючи одна одну `PassLock`, а налаштування,
збережені в одному вікні, тихо перезаписувалися б іншим.

Це стосується й автозапуску: якщо програму вже відкрито вручну, запуск із `--tray` при вході в
Windows завершиться одразу, а не додасть другий значок біля годинника.

`wfs.exe` навмисно **не** обмежений: `sync --once` із Планувальника має запускатися будь-коли, а від
накладання проходів захищає наступний замок.

### Один прохід на конфіг (`PassLock`)

`PassLock`: іменований `Mutex` `Local\WorkFlowSync.<hash шляху конфігу>` + облік у процесі (м'ютекс
Windows реентерабельний для того самого потоку). Один прохід за раз для конфігу **між усіма**: GUI
«Виконати зараз», `wfs sync --once` з Планувальника, резидентний `--loop`. Другий `--once` — код 4;
резидент — пропускає прохід із WARN; GUI — повідомлення «Інший прохід уже виконується». Покинутий
м'ютекс (процес помер посеред проходу) береться — база стану транзакційна. Це захищає від накладання проходів, коли Планувальник
запускає `--once` під час резидентного `--loop`.

## Портативність

`WorkFlowSync.exe` (GUI) + `wfs.exe` (консоль), обидва self-contained single-file, + `config.json`; `state.db` і
`logs\` створюються поруч. Папку можна перенести разом зі станом. Жодних записів у реєстр і
`%AppData%` (крім автозапуску, якщо користувач його увімкне).

## Запуск від звичайного користувача

Усі варіанти нижче не потребують прав адміністратора.

Обидва способи вмикаються перемикачами в GUI («Налаштування» → «Автоматичний запуск») або
консольно; достатньо одного.

**Резидент через автозапуск** (рекомендовано для «висить і сам перевіряє»): `wfs autostart on` —
ярлик `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\WorkFlowSync.lnk` →
`wfs.exe sync --loop --config <config>` з мінімізованим вікном (WScript.Shell COM). Запуститься
при наступному вході в Windows; щоб запустити зараз — двічі клацнути ярлик.

**Планувальник завдань** (режим «раз на N хвилин»): `wfs task on` — еквівалент

```powershell
schtasks /Create /TN "WorkFlowSync" /TR "\"D:\Tools\WorkFlowSync\wfs.exe\" sync --once --config \"…\config.json\"" /SC MINUTE /MO 30 /F
```

Без `/RL HIGHEST` і без `/RU` — завдання виконується від поточного користувача, лише коли він
увійшов, і не вимагає пароля чи адміністратора. Інтервал береться з конфігу на момент створення;
після зміни інтервалу перемикач треба вимкнути й увімкнути.

Обидва механізми вимагають `wfs.exe` поруч із `WorkFlowSync.exe` (так публікує `scripts\publish.ps1`);
у Debug-збірці GUI перемикачі неактивні з поясненням.

Вікно консолі в резидентному режимі — мінімізоване (`WindowStyle = 7` у ярлику); трей — опційний
Етап 4. Ротація логів: при відкритті логера видаляються `wfs-*.log` старші за 30 днів.

## Сценарії приймання

1. `sync --once` без конфігу → повідомлення й код 2. ✅
2. Два `sync --once` одночасно → другий завершується кодом 4, перший працює. ✅ (тест `Pass_lock_is_exclusive…`)
3. `sync --loop` + Ctrl+C посеред проходу → база не пошкоджена, лог містить «interrupted». ✅
4. `--loop` перечитує конфіг між проходами. ✅ (тест `Loop_runs_passes_on_the_interval_and_picks_up_config_edits`)
5. Після перезавантаження Windows з ярликом у Startup процес є в Диспетчері, вікно мінімізоване. (перевірити вручну)

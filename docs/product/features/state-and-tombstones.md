# F2. База стану, tombstone, локальні зміни

**Статус**: реалізовано (Етап 1, 2026-09-14). Модель: `src/WorkFlowSync.Core/Model/`; сховище:
`src/WorkFlowSync.Core/State/StateStore.cs` (SQLite, WAL, upsert однією транзакцією).

## Мета

Пам'ять програми. Саме вона замінює 22 569 ручних виключень FreeFileSync: кожен об'єкт, який
програма колись бачила, має запис із життєвим циклом.

## Сховище

SQLite, один файл `state.db` поруч з exe (шлях у конфігу `statePath`). Обрано замість JSON через
транзакційність (раптове вимкнення не ламає файл) і сотні тисяч рядків.

Робочий режим: на старті проходу таблиця читається в `Dictionary<(pair, path), StateEntry>` —
або вся (повний прохід), або лише одна тека з нащадками (`LoadScope`, для часткового проходу).
Зміни пишуться транзакціями по 2000 рядків, плюс контрольні точки під час копіювання
(`journal_mode=WAL`).

## Схема (версія 4, 2026-09-21)

```sql
CREATE TABLE entries (
  pair            TEXT NOT NULL,
  path            TEXT NOT NULL,      -- логічний відносний шлях, роздільник '\', регістр як у джерелі
  kind            INTEGER NOT NULL,   -- 0 file, 1 dir
  status          INTEGER NOT NULL,   -- 0 active, 1 tombstone, 2 local_modified
  first_seen      INTEGER NOT NULL,   -- Unix-мілісекунди UTC
  last_seen       INTEGER NOT NULL,
  src_size        INTEGER,
  src_mtime       INTEGER,
  copied_size     INTEGER,
  copied_mtime    INTEGER,
  copied_at       INTEGER,           -- час останнього успішного запису копії; NULL для старих/прийнятих файлів
  via_link        INTEGER NOT NULL DEFAULT 0,
  status_changed  INTEGER,
  remote_id       TEXT,               -- зарезервовано під сторонні сервіси (F17); поки NULL
  remote_version  TEXT,
  PRIMARY KEY (pair, path)
) STRICT, WITHOUT ROWID;

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);  -- schema_version, last_run, last_run_result
```

Версія 3 також додала таблицю `pending` для погодження змін. Версія 4 додає `copied_at`: ротація
може видаляти лише файл із цією власною позначкою, тому прийняті або успадковані старі копії не
стають кандидатами автоматично.

Порівняння шляхів — **без урахування регістру** (`OrdinalIgnoreCase`), як NTFS/SMB; у базі
зберігається оригінальне написання для відображення.

### Чому час зберігається числом

У версії 1 п'ять міток часу лежали текстом у форматі ISO-8601 з сімома знаками після коми
(33 байти кожна). На мільйоні записів це ~135 зайвих байтів на рядок і п'ять викликів
`DateTimeOffset.Parse` при кожному читанні. Мілісекундної точності більш ніж досить: планувальник
порівнює час зміни з допуском 2 секунди. Замір на 1 млн записів: файл **279 МБ → 114,7 МБ**.

### Міграція зі старих версій

Відбувається автоматично при першому відкритті старої бази:

1. узгоджена резервна копія `state.db.vN-backup` (`VACUUM INTO` — працює на «живій» базі);
2. потокове перенесення рядок за рядком у нову таблицю (не тримає базу в пам'яті);
3. `VACUUM`, інакше звільнені сторінки лишаються у файлі й мігрована база виходить **більшою** за стару.

Базу, записану новішою версією програми, ніж поточна, буде відхилено з помилкою — щоб не зіпсувати
історію.

### Читання за областю

`LoadScope(pair, тека)` читає лише цю теку й усе під нею — два діапазонні запити по первинному ключу
через `UNION ALL`. Замір: **4,1 мс проти 3,8 с** повного читання мільйона рядків.

Обмеження, яке треба знати: діапазон порівнює байти, тож тека, у якої **змінився регістр** імені,
у частковому проході не знайдеться — її підбере повний прохід. Це навмисний поділ праці: частковий
прохід приблизний, повний — джерело правди. Команда `forget`, навпаки, читає пару цілком, бо
шлях туди вводить людина.

## Статуси

| Статус | Значення | Як виникає | Що далі |
|--------|----------|------------|---------|
| `active` | Дзеркалюється | новий об'єкт у джерелі | оновлюється з джерела, поки локальна копія ціла |
| `tombstone` | Заборонено повертати | локально видалено/переміщено; вичерпано автоочищення; безпечно видалено ротацією; видалено з обох боків; батьківська папка стала tombstone | ніколи не копіюється; запис живе вічно (він і є «виключення») |
| `local_modified` | Локальна версія головна | `L ≠ copied` | джерело ігнорується; якщо L зникне → `tombstone` |

## Виявлення локальних змін

Порівняння **фактичних** `size + mtime` цілі з `copied_size + copied_mtime`, записаними одразу
після копіювання. Вміст не читається — важливо для OneDrive Files On-Demand (не гідруємо).

Ризики і рішення:

- OneDrive не змінює mtime при синхронізації — ок.
- Антивірус/індексатор не змінюють mtime — ок.
- Користувач відкрив і зберіг без змін (Word оновлює mtime) → `local_modified`. Прийнятно: правило 3
  каже «зміна локально = не чіпати».

## Каскад для папок

При переході папки в `tombstone` усі записи з префіксом `path\` теж стають `tombstone` (planner
обробляє шляхи від батьків до дітей). Якщо запис папки вже `tombstone`, сканер джерела в неї не
спускається (предикат `skipDirectory`) — це і економія, і гарантія правила 3.

## Обслуговування

- `status` показує лічильники за статусами і розмір бази.
- `forget <шлях>` (Етап 2) — видалити запис(и), щоб об'єкт з'явився заново як новий.
- Ключ пари — `name` з конфігу; перейменування пари осиротить її записи (задокументовано в F6).

## Сценарії приймання

1. Після першого проходу кількість `active` = кількості об'єктів у джерелі (мінус виключення).
2. Вимкнення живлення під час запису стану → наступний запуск відкриває базу без помилок; втрачено
   щонайбільше результати одного проходу.
3. 500 тис. записів: завантаження в пам'ять < 3 с, запис проходу < 5 с (орієнтир, SSD).
